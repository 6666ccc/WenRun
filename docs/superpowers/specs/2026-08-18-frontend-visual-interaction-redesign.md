# 温润诊所患者端前端视觉与交互重构设计

日期：2026-08-18  
状态：设计定稿 v1.1，已纳入用户提供的配色参考，待 Luna 实施  
范围：患者端 Vue 3 前端的视觉系统、信息架构、页面布局、交互状态、响应式与无障碍。  
明确边界：本文不修改后端接口、数据结构、鉴权机制或 AI 工作流；实施时不得用虚假数据伪造后端尚未提供的能力。

## 1. 结论先行

重构采用“清爽临床薄荷绿”方向，但不把页面铺满绿色。深青绿用于品牌与可点击的主操作，明亮薄荷绿只用于焦点、强调与轻量装饰，大面积保持白色和极浅薄荷底；红/橙/蓝只服务于危险、提醒和信息状态。

产品结构从当前“新版 AI / 传统版”二选一，收敛为一个统一患者端：

- 登录后直接进入首页，不再强制经过模式选择页。
- AI 改名为“健康助手”，成为一级导航，而不是另一套产品。
- 挂号、缴费、科室、档案继续保留确定性页面；AI 可以引导进入这些页面，但不能替代用户对挂号、取消和支付的最终确认。
- 桌面与移动端共享同一套视觉语言、组件与内容层级，不再维护两套明显不同的皮肤。

一句话体验目标：**患者打开系统后，3 秒内看懂下一步，3 次以内操作到达挂号、缴费或健康助手，并在重要操作前后都得到明确反馈。**

## 2. 设计依据

本方案参考了以下官方资料，并结合当前代码与页面截图形成：

1. [NHS App：应用结构](https://design-system.nhsapp.service.nhs.uk/patterns/the-structure-of-the-nhsapp/)指出，医疗用户通常带着明确任务进入应用，因此结构应按患者理解的医疗任务组织。
2. [NHS App：Hub 页面](https://design-system.nhsapp.service.nhs.uk/patterns/hub-page/)把 Home 作为安排与管理医疗服务的主要入口，并以稳定的底部导航连接核心区域。
3. [NHS App：页面间导航](https://design-system.nhsapp.service.nhs.uk/patterns/navigate-the-nhs-app/)强调每页只有一个清晰、唯一的主标题，预约完成后还应帮助用户回看记录以确认成功。
4. [NHS：错误摘要](https://service-manual.nhs.uk/design-system/components/error-summary)要求表单错误既有页级摘要，也在对应字段旁显示，并把焦点移到错误区域。
5. [NHS：按钮](https://service-manual.nhs.uk/design-system/components/buttons)建议交易流程减少竞争性主按钮，移动端扩大按钮触达面积，并防止重复提交。
6. [VA Design System：Card](https://design.va.gov/components/card/)明确卡片不应替代表格、表单分组或所有导航；只有需要强调状态或行动的内容才应卡片化。
7. [WCAG 2.2](https://www.w3.org/TR/WCAG22/)作为无障碍基线，重点落实文字对比度、键盘操作、焦点可见、回流和最小点击目标。
8. [WHO：医疗 AI 六项原则](https://www.who.int/news/item/28-06-2021-who-issues-first-global-report-on-ai-in-health-and-six-guiding-principles-for-its-design-and-use)强调人的自主权、安全、透明、可解释和责任，因此 AI 页面必须显式说明能力边界，并让用户确认重要操作。

### 2.1 用户提供的视觉参考如何使用

新增的两张截图只作为**配色、边框、层级与控件质感参考**，不是页面结构或业务流程指令：

- 图 1 提取“白色表单卡 + 极浅薄荷背景 + 青绿焦点边框 + 青绿主按钮 + 柔和绿色投影”的轻盈登录体验。
- 图 2 提取“白色工作区 + 薄荷提示条 + 青绿操作按钮 + 极浅分隔线 + 信息分区”的临床系统可信赖感。
- 图 2 是医生侧的高密度详情工作台，**不得**照搬到患者端；患者端仍以任务入口、清晰摘要和低认知负担为优先。

## 3. 现状审查

### 3.1 当前优点

- 登录页已有完整品牌氛围，桌面左右分栏和移动端单卡片结构均能正常回流。
- 已存在一套 CSS 变量、间距、圆角、状态色和 Lucide 图标封装，不需要从零搭建。
- 列表页普遍具备加载、错误、空状态，挂号和支付也有基本确认逻辑。
- 桌面侧栏、移动底栏和表格转卡片的响应式骨架已经存在。
- AI 已有会话、引用、停止生成、挂号中断确认和急症提示等关键状态。

### 3.2 最高优先级问题

1. **产品身份割裂。** 登录后要求患者选择“新版 AI”或“传统版”，两边视觉、导航和语言均不同，用户需要先理解版本，而不是直接完成任务。
2. **视觉变量与页面硬编码并存。** 主系统使用 `--c-*`，AI/模式页大量使用另一组硬编码颜色；`index.css` 和 `views.css` 合计接近 2000 行，存在未被模板引用的旧 `.ai-*`、日期选择器和表单样式。
3. **绿色主张不明确。** 当前主品牌偏蓝灰与暖金，AI 页面又使用青绿，登录页和业务页看起来像两个不同品牌。
4. **过多“小字 + 卡片 + 弱对比”。** 当前存在约 9–11px 的说明文字，琥珀色、鼠尾草绿、暖灰在白底上的对比度不足以承担普通文本。
5. **交易流程过于压缩。** 挂号在单个弹窗中选择排班并立即提交，支付详情直接确认，没有完整的“选择—复核—结果”心理模型。
6. **可访问性缺口。** 多个 `label` 未通过 `for/id` 关联输入框；科室卡片用 `article @click`，无法自然键盘操作；Dialog 缺少语义、焦点圈定、Esc 关闭和关闭后焦点归还；异步消息缺少 live region；图标按钮缺少可访问名称。
7. **状态反馈位置不稳定。** 成功/失败多以普通卡片插入，容易引发布局跳动，也未明确告诉用户“接下来做什么”。
8. **AI 信任表达有偏差。** “随身诊室”“智能体在线”可能被理解为真实医生或可靠在线状态；急症判断只依赖前端关键词不能作为安全保障。

### 3.3 当前颜色对比风险

以当前卡片底色 `#FFFDF9` 计算：

| 颜色 | 对比度 | 结论 |
|---|---:|---|
| `#3D5A5C` 品牌深色 | 7.34:1 | 可用于正文和按钮 |
| `#C8944A` 琥珀色 | 2.65:1 | 只能做装饰或大图形，不能承担普通文字 |
| `#8C8278` 次要文字 | 3.70:1 | 普通小字号风险高 |
| `#B8B0A6` 弱文字 | 2.11:1 | 不可用于有意义的小字 |
| `#7A9E85` 成功色 | 2.93:1 | 不能仅靠此色表达状态 |
| `#C47A7A` 危险色 | 3.22:1 | 错误正文对比不足 |

## 4. 信息架构

### 4.1 统一一级导航

桌面侧栏从上到下：

1. 首页 `/home`
2. 健康助手 `/assistant`
3. 预约挂号 `/registration`
4. 门诊缴费 `/payment`
5. 科室医生 `/department`
6. 我的档案 `/user`

移动底栏固定 5 项：

1. 首页
2. 挂号
3. 健康助手（中间主入口，但不做夸张悬浮球）
4. 缴费
5. 我的

科室医生从首页服务区和挂号流程进入，不占移动底栏。

### 4.2 路由处理

- `/login`：登录/注册。
- `/mode-select`：保留兼容入口，但登录后不再主动跳转；进入该地址时重定向 `/home`。
- `/home`：统一首页。
- `/assistant`：统一壳内的健康助手。
- 其余既有业务路由保持不变，避免影响后端契约与外部书签。
- 已登录访问 `/login` 时跳 `/home`，不再依据旧 mode 决定落点。

### 4.3 页面优先级

页面内容按以下顺序组织：

1. 必须立刻处理：待缴费、即将就诊、急症提示、操作失败。
2. 最常用操作：挂号、健康助手、缴费、查记录。
3. 历史信息：已完成预约、已支付订单、既往就诊。
4. 低频设置：个人档案、退出登录。

## 5. 视觉系统

### 5.1 色板

| Token 建议名 | 色值 | 用途 |
|---|---|---|
| `color-brand-900` | `#12443B` | 侧栏、深色品牌区 |
| `color-brand-800` | `#006B5A` | 主按钮悬停、深色强调 |
| `color-brand-700` | `#007A68` | 主按钮、活动导航、链接；白底文字对比 5.27:1 |
| `color-brand-600` | `#008271` | 主色补充、选中边界；白底文字对比 4.74:1 |
| `color-mint-500` | `#00B89C` | logo 图形、细边高光、focus glow；不可放白色正文 |
| `color-mint-200` | `#CDEFE7` | 输入框悬停、轻边框、提示条边界 |
| `color-mint-100` | `#E8F8F4` | 选中背景、轻提示 |
| `color-mint-050` | `#F3FBF9` | 页面局部浅底、登录背景 |
| `color-bg` | `#F6FBF9` | 页面背景 |
| `color-surface` | `#FFFFFF` | 卡片、弹层、表单 |
| `color-text` | `#12342D` | 主正文；白底对比 13.51:1 |
| `color-text-secondary` | `#51645F` | 次要正文；白底对比 6.29:1 |
| `color-border` | `#D9EEE8` | 默认边框与分隔线 |
| `color-success` | `#087A55` | 成功图标/文字；配图标与文字 |
| `color-warning` | `#9A6700` | 提醒；配浅黄底 |
| `color-danger` | `#B42318` | 错误、取消、急症 |
| `color-info` | `#176B87` | 普通信息、引用 |

规则：

- 绿色不用于所有容器，只用于品牌、主操作、选中态和少量强调；默认业务面保持白底。
- `brand-700` 是唯一允许承载白色主按钮文字的绿色；`mint-500` 只作高光、图形和 focus glow，不作文字或整块按钮底色。
- 登录页和轻量空状态可用 `mint-050` 径向渐变；业务详情页只用纯白内容面与 1px 薄荷边框，避免“医疗后台荧光感”。
- 成功、危险、警告、信息都有“浅背景 + 深文字 + 图标 + 文案”，不得只改文字颜色。
- 金色只保留为极少量品牌点缀，不再用于正文、价格或主按钮。
- 价格默认使用主文字色；只有“待支付”状态用 warning，不用金色制造促销感。

### 5.2 字体与字号

不再依赖 Google Fonts 网络请求。建议字体栈：

`PingFang SC, Microsoft YaHei, Noto Sans CJK SC, system-ui, sans-serif`

品牌字可保留宋体作为小范围装饰，但页面标题、表单、表格和 AI 正文统一无衬线。

| 层级 | 桌面 | 移动 | 字重/行高 |
|---|---:|---:|---|
| 页面 H1 | 28px | 24px | 600 / 1.35 |
| 区块 H2 | 20px | 18px | 600 / 1.4 |
| 卡片标题 | 16px | 16px | 600 / 1.5 |
| 正文 | 16px | 16px | 400 / 1.65 |
| 辅助文字 | 14px | 14px | 400 / 1.55 |
| 标签/徽标 | 12px | 12px | 600 / 1.4 |

禁止小于 12px 的可见文本；AI 免责声明在移动端仍至少 12px。

### 5.3 空间、圆角和阴影

- 采用 4px 基础网格：4 / 8 / 12 / 16 / 24 / 32 / 40 / 48。
- 页面区块间距 24px，卡片内部 20–24px，表单字段间距 20px。
- 控件圆角 10–12px，卡片 16px，弹层 20px，徽标胶囊形。
- 默认卡片使用 `1px solid color-border`，无阴影；仅登录卡、浮层、悬停卡片和固定输入区使用 `0 12px 28px rgba(0, 122, 104, .08)` 级别的轻阴影。
- 输入框默认白底与浅薄荷边框；hover 提高到 `mint-200`，focus 使用 `brand-700` 的 2px 边框 + `mint-500` 的 3px 外发光。
- 不使用大面积纹理、颗粒或多重渐变；仅登录背景或空状态可以有一个不影响文字识别的极弱薄荷径向光晕。

### 5.4 控件尺寸

- 桌面输入框/普通按钮最小高度 44px。
- 移动端主按钮和输入框高度 48px。
- 图标按钮可见图标 20px，点击区域至少 44×44px。
- 移动底栏高度 64px + safe area。
- Focus ring：外侧 3px `rgba(0,184,156,.24)`，同时保留 2px `brand-700` 边界，任何控件都不得 `outline: none` 后无替代。

### 5.5 动效

- 普通 hover/focus：160ms。
- 抽屉/弹层：220ms。
- 页面不做整屏进入动画；列表最多轻微淡入，不逐个延迟超过 240ms。
- 加载超过 300ms 才显示 skeleton，避免闪烁。
- 全局支持 `prefers-reduced-motion: reduce`，关闭位移、脉冲和自动平滑滚动。

## 6. 全局布局

### 6.1 桌面端（≥1024px）

- 左侧栏宽 248px，固定全高，背景 `brand-900`。
- 顶栏高 64px，只显示当前页面位置、帮助入口和个人菜单；不重复品牌口号。
- 主内容最大宽 1180px，左右 padding 32px；1440px 以上为 40px。
- 侧栏活动项为浅绿透明背景 + 左侧 3px 指示条 + 文字/图标同时变化。
- 用户信息位于侧栏底部，点击进入个人菜单；退出登录放菜单内，避免一直显示危险按钮。

### 6.2 平板（768–1023px）

- 侧栏收窄为 80px，仅图标；hover/focus 和 tooltip 显示名称。
- 主内容 padding 24px。
- 业务双栏降为单栏；详情页重要摘要保持顶部。

### 6.3 移动端（≤767px）

- 页面 padding 16px；主内容底部预留 `64px + safe-area + 16px`。
- 顶栏 56px，左侧返回/标题，右侧最多一个主操作。
- 底栏始终保持 5 项；只有全屏确认弹层和输入键盘状态可覆盖它。
- 表格转为语义化列表，不强行横向滚动；确需比较的费用明细表可水平滚动并固定首列。
- 页面主 CTA 在长表单和详情页可使用底部 sticky action bar，但不能遮挡内容与键盘焦点。

## 7. 页面设计

### 7.1 登录与注册

桌面保持左右分栏，但改为 44% 品牌区 + 56% 表单区，减少左侧空白。品牌区使用深青绿、极弱薄荷光晕和一句核心承诺；表单区使用 `mint-050` 的白底渐层，卡片宽 420px。登录卡为白色、14–16px 圆角、薄荷细边框与非常轻的绿色投影，复刻图 1 的干净感而非旧版的厚重纸张感。

登录卡片顺序：Logo/名称 → 标题 → 说明 → 页级错误 → 用户名 → 密码（带显示/隐藏）→ 登录 → 注册入口 → 演示账号。

交互要求：

- 每个 label 必须关联 input；用户名、密码、手机号配置正确 autocomplete 和 inputmode。
- 点击提交后按钮保留宽度并显示 spinner，禁止重复提交。
- 错误摘要获得焦点；对应字段边框、错误图标和字段级文案同步出现。
- 注册采用同一卡片内切换，不做 3D 翻页；切换时标题和焦点回到第一个字段。
- 注册字段分两组：“账户信息”“患者联系方式”，身份证等敏感档案不放在初次注册，登录后再完善。
- 移动端不显示独立品牌侧栏，保留紧凑 Logo 和一句说明；卡片顶部距视口 48–72px，不垂直强制居中，避免小屏键盘遮挡。
- 主按钮使用 `brand-700` 白字，hover/pressed 降到 `brand-800`；输入框 focus 的亮薄荷只作为外圈提示，不以低对比色承载文字。

### 7.2 首页

首页不是数据看板，而是“下一步行动中心”。从上到下：

1. 问候与日期，右侧为“健康助手”轻量按钮。
2. `下一步` 状态卡：优先显示最近预约；无预约时显示“还没有预约，开始挂号”；有待缴费时作为第二条提醒。
3. 核心服务：挂号、健康助手、缴费、科室医生、就诊记录、我的档案。桌面 3×2，移动 2×3。
4. `近期记录`：最近 3 条挂号/就诊，以列表行呈现，不再把每条数据做卡片。
5. `今日可预约`：最多 4 条排班，显示科室、医生、时段、余号和费用；操作为“查看号源”。

首页移除纯数字统计卡，除非数字能直接推动行动。待缴金额、下一次预约比“总挂号数”更有价值。

### 7.3 科室医生

桌面使用主从布局：左侧 320px 科室列表，右侧医生列表；移动端改为科室可展开列表。

- 搜索框固定在标题下，支持科室名/编码；清除按钮有可访问名称。
- 科室项必须是 `button` 或 link，不再给 `article` 绑定 click。
- 选中科室显示独立的活动态，不使用仅靠顶边金线的样式。
- 医生行显示姓名、职称、科室；只有有可用排班时才显示“查看号源”。
- 加载医生时只对右侧结果区显示 skeleton，不让整个页面重载。
- 搜索无结果时保留搜索词并提供“清除搜索”。

### 7.4 预约挂号列表

页面顶部为 H1、说明和唯一主按钮“预约挂号”。主体分为“待就诊”和“历史记录”两个标签页，默认待就诊。

桌面列表列：就诊日期/时段、科室医生、患者、状态、费用、操作。挂号编号降为次要信息，不占第一列。移动端为纵向列表：日期作为视觉锚点，下面是科室医生和状态。

每行主要操作是“查看详情”；取消属于危险次操作，放入 `更多` 菜单或详情页，避免误触。

### 7.5 预约挂号流程

桌面使用宽 720px 的 Dialog，移动端使用全屏 Drawer。流程分 4 步，并在顶部显示短步骤条：

1. 选择科室。
2. 选择日期和医生/号源。
3. 选择时段。
4. 核对并确认。

若现有接口只返回当天排班，日期区域只显示有数据的日期，不伪造未来号源。

复核页必须显示：患者、科室、医生、日期、时段、挂号费、余号提示。主按钮文案为“确认挂号 ¥X”，次按钮为“返回修改”。

提交状态：按钮 spinner + 页面其他选项锁定；成功后不要只 toast，显示明确结果面板：

- `挂号成功`
- 挂号编号
- 就诊日期/时段
- 科室/医生
- “查看挂号详情”主操作
- “返回首页”次操作

### 7.6 挂号详情与就诊记录

- 页面顶部显示返回链接、状态、科室医生和就诊时间，时间是最大的信息锚点。
- 基础信息使用两列 summary list，不再用大量等权小方格。
- 就诊、处方、检查按时间线组织；没有关联记录时说明“就诊完成后可在这里查看”。
- 退号放页面底部危险区，按钮为次级危险样式。
- 退号确认说明后果：“号源将释放，已支付费用的退款规则以医院处理结果为准”，并再次显示挂号对象。

### 7.7 缴费列表

顶部只保留一张待处理摘要：`待缴 X 笔，共 ¥Y`，主按钮进入第一笔或列表。已缴数量不需要做等权统计卡。

主体使用“待缴费 / 已缴费”标签页：

- 待缴列表突出费用名称、创建时间、金额和“查看并支付”。
- 已缴列表突出支付时间、金额、方式和状态。
- 每笔收费单可展开查看 2–3 个明细，完整明细进入详情。
- 订单号为辅助信息，支持复制，但不抢占标题层级。

### 7.8 支付详情

桌面两栏：左侧收费明细，右侧 sticky 支付摘要；移动端单栏，底部 sticky 确认栏。

- 明细表的金额右对齐；合计与列表用分隔线区分。
- 支付方式用原生 radio 语义，不用仅视觉选中卡片。
- 确认区显示支付对象、总金额和支付方式。
- 主按钮文案必须包含金额：`确认支付 ¥123.00`。
- 提交后禁止重复点击；失败保留所选支付方式并显示可恢复文案。
- 成功后显示结果页/结果面板，并提供“查看已缴记录”和“返回首页”。
- 不用纯绿色 toast 作为唯一成功证据。

### 7.9 我的档案

页面由“身份摘要”“基本信息”“健康信息”“账户操作”四区组成。

- 身份证默认脱敏，如 `3401********1234`；提供“显示完整信息”需明确点击。
- 出生日期使用 `input[type=date]`；手机号使用 `inputmode=tel`；性别使用语义化 select/radio。
- 过敏史单独使用 textarea，并增加提示：“没有已知过敏可填写‘无’”。
- 编辑时在页面底部提供“保存修改 / 取消”，有未保存内容离开时提示。
- 退出登录放账户操作区或头像菜单，不与档案编辑主操作竞争。

### 7.10 健康助手

命名统一为“温润健康助手”，避免“随身诊室”暗示 AI 是医生。AI 页面继续使用统一 AppShell。

桌面布局：主聊天区最大宽 760px；1280px 以上显示 280px 就诊上下文栏；历史会话通过左上角按钮打开抽屉，不再叠加第二个永久侧栏。移动端上下文变为聊天顶部的 2–3 个横向信息 chip。

欢迎状态：

- 标题：“你好，我能帮你处理什么？”
- 说明：“我可以协助分诊、查询和办理；不能替代医生诊断。”
- 快捷问题控制在 4 个，使用患者语言，不用技术术语。
- 快捷业务入口：预约挂号、查看待缴、查看就诊记录。

对话状态：

- 用户消息深绿浅色系，AI 消息白底；正文 16px/1.7。
- AI 回复顶部标记“AI 生成”，引用来源折叠为“查看依据（N）”。
- 生成状态使用文本“正在查询号源 / 正在整理信息”，不要只显示跳动圆点。
- 停止按钮使用明确文案并保持 44px 点击区。
- 输入框默认 1–4 行，自增长；Enter 发送，Shift+Enter 换行，中文输入法组合态不误提交。
- 底部免责声明常驻但不小于 12px。

安全与确认：

- 聊天顶部提供固定的紧急提示入口：“如有胸痛、呼吸困难、意识障碍或大量出血，请立即拨打 120 或前往急诊。”
- 急症提示使用高优先级 danger alert，必须位于最新回复前并被屏幕阅读器播报。
- 前端关键词只能补充视觉提醒，不能成为唯一安全判断；服务端没有明确 safety intent 时不得宣称已完成医学风险识别。
- 挂号中断确认显示患者、科室、医生、日期、时段、费用；按钮是“返回修改”和“确认挂号”，不用“拒绝”这种机器流程语言。
- 任何支付、挂号、取消操作都必须由用户在结构化确认面板中完成。
- 会话删除需二次确认，成功后提供短时撤销。

## 8. 组件设计合同

Luna 应先稳定组件，再逐页替换：

| 组件 | 必须支持的状态 |
|---|---|
| `AppShell` | desktop/tablet/mobile、active route、safe area |
| `PageHeader` | title、description、back、最多一个 primary action |
| `Button` | primary/secondary/tertiary/danger、loading、disabled、icon、full-width mobile |
| `FormField` | label、hint、required、error、success、autocomplete |
| `StatusBadge` | icon + label + semantic color，不能只靠颜色 |
| `Alert` | info/success/warning/danger、title、body、optional action、live region |
| `Toast` | success/info/error、自动关闭、手动关闭；不能承载唯一重要结果 |
| `Dialog/Drawer` | title、description、focus trap、Esc、backdrop、return focus |
| `Tabs` | keyboard arrow navigation、active indicator、对应 panel |
| `SummaryList` | label/value、responsive stacking、sensitive masking |
| `DataList` | loading/empty/error、desktop row/mobile row |
| `Skeleton` | 与真实内容尺寸一致、无无限脉冲 |
| `EmptyState` | 原因、下一步 CTA、可选图标 |
| `StepFlow` | current/completed/upcoming、back、review、success |
| `ChatComposer` | IME、auto-grow、send/stop、disabled reason、safe-area |

组件规则：

- Card 是承载信息的容器，不是默认按钮；可点击区域使用真实 link/button。
- 一个视区只保留一个视觉主按钮；次级操作不得与主操作同色同权重。
- icon-only button 必须有 `aria-label` 和 tooltip。
- 所有状态组件都接受可读文本，不允许只传颜色值。

## 9. 状态与反馈矩阵

| 场景 | 页面反馈 | 控件反馈 | 可访问性 |
|---|---|---|---|
| 初次加载 | 300ms 后显示 skeleton | 主操作暂不可用 | `aria-busy=true` |
| 局部刷新 | 只刷新结果区域 | 保留筛选和滚动位置 | 更新后礼貌播报 |
| 提交中 | 内容不跳动，显示处理中 | 按钮 spinner，防双击 | 按钮名称包含“处理中” |
| 表单错误 | 顶部错误摘要 | 字段级错误 + 焦点 | `role=alert`，错误关联字段 |
| 网络错误 | 原位置错误面板 | 提供“重新加载” | 不清空已填内容 |
| 空数据 | 解释原因 | 给下一步 CTA | 不用只有插图 |
| 成功 | 稳定结果面板 | 主 CTA 指向下一步 | `role=status` |
| 危险操作 | 确认后果和对象 | 危险按钮与取消分离 | focus trap + return focus |
| 无权限/会话过期 | 说明已退出原因 | “重新登录” | 不静默跳转 |

## 10. 无障碍验收基线

目标为 WCAG 2.2 AA，不在仅凭视觉验收时宣称完全合规。

- 普通文字对比度 ≥4.5:1，大字 ≥3:1，图标/边界等非文本关键元素 ≥3:1。
- 360px 宽和 200% 缩放不出现双向滚动；表格例外必须有可见滚动提示。
- 全站可仅用键盘完成登录、挂号、取消、缴费、编辑档案和 AI 确认。
- 焦点顺序与视觉顺序一致；sticky composer/底栏不得遮挡焦点。
- 每页一个唯一 H1；标题层级连续；导航使用 `nav` 与 `aria-current=page`。
- 表单 label 与 input 关联；必填、提示、错误通过 `aria-describedby` 连接。
- Dialog 打开时焦点进入，Tab 不逃逸，Esc 关闭，关闭后回到触发按钮。
- 动态成功、失败、急症和 AI 状态通过合适的 live region 播报。
- 所有图标有明确语义或 `aria-hidden=true`；装饰性图形不进入阅读顺序。
- 不用颜色、左右位置、形状单独传达状态。
- 全局响应 `prefers-reduced-motion`。

## 11. Luna 实施顺序

### Phase 1：清理与设计 Token

1. 盘点并移除未使用的 `.ai-*`、`view-form-input`、日期选择器等死样式。
2. 将颜色、字体、间距、圆角、阴影、层级和动效统一成 semantic tokens。
3. `index.css` 只保留 reset、tokens、base 和极少工具类；页面样式按组件/视图拆分，避免继续扩充单个 1000+ 行 CSS。
4. 移除 Google Fonts `@import`，使用本地系统字体栈。

### Phase 2：基础组件

1. 重构 Button、FormField、Alert、StatusBadge、UiState、Dialog/Drawer。
2. 补齐 focus、loading、error、disabled、keyboard 和 aria 行为。
3. 建立 desktop/mobile DataList 与 SummaryList。

### Phase 3：统一壳与导航

1. 重构 AppShell、侧栏、顶栏、移动底栏。
2. 将 Assistant 放回 AppShell。
3. 登录后跳转 `/home`，兼容处理 `/mode-select`。
4. 更新与 mode 入口相关的前端测试。

### Phase 4：高价值流程

1. 登录/注册。
2. 首页。
3. 挂号列表、4 步挂号、挂号成功、挂号详情、退号确认。
4. 缴费列表、支付详情、支付成功。

### Phase 5：其余页面与 AI

1. 科室医生。
2. 我的档案与敏感信息脱敏。
3. 健康助手的统一布局、引用、紧急提示、结构化确认和移动端 composer。

### Phase 6：验证

1. 运行现有 build、lint、unit tests。
2. 新增关键交互测试：模式入口迁移、Dialog 键盘、表单错误、挂号复核、防双击、支付复核、AI 中断确认。
3. 视口至少验证 360×800、390×844、768×1024、1024×768、1440×900。
4. 键盘走查与 200% zoom 走查。
5. 对关键色对运行自动 contrast 检查，并人工核对状态不依赖颜色。

## 12. 验收标准

### 全局

- [ ] 登录后不再要求选择“新版/传统版”。
- [ ] 所有患者页面使用同一 AppShell、色板、字号、按钮和状态语言。
- [ ] 无未引用的大段旧 CSS；页面样式职责清晰。
- [ ] 绿色是明确品牌色，但正文区仍以白/浅灰绿为主。
- [ ] 主要操作在桌面和移动端均能一眼识别。
- [ ] 任一页面没有小于 12px 的可见文字。

### 交互

- [ ] 登录、挂号、支付、档案保存均有 loading、防双击、错误恢复和成功下一步。
- [ ] 挂号和支付均有结构化复核，不从选项直接跳到“成功”。
- [ ] Dialog/Drawer 支持键盘、Esc、focus trap 和 return focus。
- [ ] 页面刷新失败不会清空筛选或表单内容。
- [ ] AI 挂号确认使用患者语言，且用户可以返回修改。

### 响应式

- [ ] 360px 无页面级横向滚动。
- [ ] 底栏、sticky action 和 chat composer 不互相遮挡。
- [ ] 桌面数据列表在移动端转换为可读列表，不只是缩小字体。
- [ ] 键盘弹出时登录/注册和 AI 输入仍可操作。

### 信任与安全

- [ ] AI 明确标记为 AI，不自称医生或诊室。
- [ ] 急症提示醒目、可播报，并明确 120/急诊行动。
- [ ] 重要成功结果不只依赖 toast。
- [ ] 身份证等敏感字段默认脱敏。
- [ ] 状态不只依赖红/绿颜色。

## 13. 非目标

- 不修改任何 Java/Python 后端接口与 AI graph。
- 不新增医生端、管理端或消息中心。
- 不实现真实第三方支付、短信、推送或身份证核验。
- 不加入暗色模式。
- 不引入大型 UI 框架来替代现有 Vue 组件。
- 不用假医生头像、假排班或假健康数据装饰页面。
