# RAG 解析与切分验收评估

评估日期：2026-09-30。对象为当前工作区代码，包括尚未提交的改动。本次只评估，没有修改业务实现。

## 结论

主要能力已经落地，常规样本的修复有效；但还不能认为整份《知识库文档解析与切分改进计划》已经基本验收通过。存在两项优先修复的问题：真实 PDF 的标题及数字被重新排序，且质量门禁没有发现；同段多个 Word 公式会失去相应的解释文字。

《企业级RAG知识库与检索评估指南》作为参考框架使用，没有把其中所有业界建议都当成此次必须实现的功能。当前能够证明部分解析、切分规则生效，不能证明真实检索的 Recall@5、MRR 或回答正确性已经提升。

## 验证范围与方法

- 阅读两份目标文档，对照解析、清洗、切分、质量检查、索引适配及发布审核代码。
- 运行解析与指标专项测试、相关 RAG 回归测试以及完整 Python 单测。
- 对仓库 `ai-python/data/knowledge_sources/` 的 10 份实际 PDF 重新解析并检查结构与质量报告。
- 将《居民体重管理核心知识（2024年版）释义》的第 1、4 页渲染成图片，与解析输出和原有纯文本提取结果核对。
- 额外构造同段双公式、超长表格单行、超长公式、连续三页段落、表格内化学式与重复检索 ID 等边界样本。

额外切分探针和实际 PDF 的切分检查使用字符分词器（一个字符一个 token），用于确定性检查切分算法；不是生产 Qwen tokenizer 的长度测量。PDF 标题、阅读顺序异常发生在切分之前，不依赖该分词器。本次没有调用在线 embedding/LLM，没有写入或重建线上索引，没有进行 2 核 4G 资源压力测试。

## 优先修复的问题

### 1. [P1] 真实 PDF 内容错序，质量报告仍为 pass

位置：`ai-python/app/rag/ingestion/pdf_layout.py:68`、`:122`、`:161`、`:253`。

使用实际资料 `nhc_resident_weight_management_knowledge_explained_2024.pdf` 复现，并核对了第 1、4 页的渲染图。

- 第 1 页完整标题是“居民体重管理核心知识（2024年版）释义”，解析后却将“年版）”作为独立文档标题；其余标题进入另一元素。
- 第 4 页正文原有“0.5 公斤”“3～6 个月”“5%～10%”“65 岁及以上”。解析后这些单位、数字和文字被搬到页首，并组成错误标题：`公斤的速度3个月内减少体5%岁及以上老年人不宜盲目减重`。
- 正文相应位置变成“每周体重减少不超过 0.5 ，在 ~6”“重的 ~10%”“65 ，重点是……”，section_path 也带上了上述假标题。
- 该文档的确定性质量报告仍是 `pass`。

证据表明，visitor 回调中的部分坐标与字号异常未经校验就进入坐标排序及字号标题判断。例如“年版）”被记录为 x=0、y=841.9、font_size=439，而同一标题其他文字的字号约为 21.95。原页面与直接 `page.extract_text()` 的内容顺序均正常。

建议：优先处理异常坐标/字号的检测与可靠回退，避免将异常 run 移到其他行；之后再进行行聚类和标题识别。把此文件第 1、4 页加入固定回归集，断言标题完整、数值与单位保持相邻、正文不被提升为标题。质量检查需能暴露异常版面信息。

### 2. [P1] Word 同段多个公式失去对应解释

位置：`ai-python/app/rag/ingestion/parsers.py:316`、`ai-python/app/rag/ingestion/chunking.py:574`。

构造同一个段落：`Formula A: [x²] where x is height. Formula B: [y²] where y is weight.`

当前解析先把段落中的普通文字全部合成一个正文元素，再把两个公式追加到正文之后。切分结果为：

```text
片段 1：Formula A: where x is height. Formula B: where y is weight.
        {x}^{2}
片段 2：{y}^{2}
```

第二个公式完全没有解释，第一个公式则混入了第二个公式的解释。这直接不满足“公式片段都包含至少一句解释文字”的验收要求。单独公式段的现有测试无法发现该问题。

建议：按段落 XML 子节点的真实顺序输出正文/公式；避免用消耗式 pop 让相邻公式争抢解释。新增同行双公式、共享解释、公式前后均有文字的用例。

### 3. [P2] 超长表格单行可以突破 max_tokens

位置：`ai-python/app/rag/ingestion/chunking.py:658`。

`_table_row_windows` 只在当前窗口已有一行时才检查超限；一个数据行加表头本身超长时，会原样输出。

字符分词器、预算 32 的探针中，`Name | Dose` 表头加一个长数据行产生了 121-token 片段，质量状态仍是 pass。现有长表测试也没有断言每段实际长度不超过预算。

建议：明确超长单行策略，可在保留字段名与表头上下文的前提下拆分单元格，或转审核/阻断；不要静默输出超限片段。长度验收还应考虑最终附加的文档名和章节前缀。

### 4. [P2] 超长公式会被硬切，仍产生无解释片段

位置：`ai-python/app/rag/ingestion/chunking.py:225`。

普通短公式路径有效，但超长路径直接调用 `_window`。预算 32 的探针产生只包含公式中间部分的片段，以及仅含 `nation after.` 的解释尾段。

建议：公式本身过长时转人工审核；可容纳的公式则保留公式整体，并将解释压缩或重复到相应片段，避免恢复成普通 token 硬切。

### 5. [P2] 连续三页段落在第三页断开

位置：`ai-python/app/rag/ingestion/pdf_layout.py:407`。

第 1、2 页合并后，元素 page_number 仍为 1。第 3 页比较 `3 == 1 + 1`，因此无法继续合并。探针输出页码分别为 `[1, 2]` 和 `[3]` 的两个元素。

建议：使用前一元素 provenance 的最后一页判断相邻页，并覆盖三页以上连续段落；英文句号结尾应阻止跨页合并。

## 其他缺口

1. **表格内化学式未还原。** `parsers.py:432` 使用 `cell.text.strip()`，表格内的下标 H₂O 实测成为 H2O。表格内 OMML 也没有复用段落公式提取流程。
2. **search_text 未贯通索引。** `adapter.py:18` 使用 `chunk.text`，Chunk 没有独立的 search_text。普通段落 Ca²⁺ 的元素检索投影是 Ca2+，但最终 page_content 仍只有 Ca²⁺。这是双文本表示尚未接入的问题；不能据此直接断言当前向量检索一定失败。
3. **部署仍安装重型可选依赖。** `Dockerfile:6` 仍是 `pip install ".[ingest]"`；该 extra 包含 Docling 和 transformers。默认 native 解决了误启用，未满足计划“不在线上部署重型解析工具”的依赖约束。默认 tokenizer 又依赖 transformers，需要把必要分词依赖与可选重型解析依赖分开核实。本次未构建镜像，也未测量运行内存。
4. **检索评估还只有计算函数。** `evaluation.py` 可以计算 Recall、Precision、Hit、MRR、nDCG；未找到读取人工标注题集、运行真实检索并输出前后对比的入口。线上仍是纯向量 top-5、阈值 0.8。BM25、RRF、重排等是指南建议，不作为本次解析修复必做项。
5. **指标函数未约束重复结果。** `ndcg_at_k(['a'], ['a', 'a'], 2)` 实测为 1.63093。评估前应去重或拒绝重复 chunk ID，避免融合结果使指标失真。

## 建议的验收顺序

1. 修正真实 PDF 阅读顺序与标题，并修正 Word 同段多公式的源顺序和解释绑定。
2. 补齐超长表格单行、超长公式、三页段落、表格内公式与上下标的边界处理和回归断言。
3. 同步引用字段测试，检查部署依赖，补上质量报告的管理界面或明确可用的审核操作入口。
4. 固定 20～30 份代表性资料；建立人工审核问题集，用同一份资料和问题对比改动前后的 Recall@5、MRR。切分变化后宜以文档、页码、证据文字等稳定标签映射相关片段，避免直接复用已变化的 chunk ID。

完成前两步后，可以重新判断解析切分是否达到“基本满足”；真实检索效果是否提升，需要第四步提供独立证据。
