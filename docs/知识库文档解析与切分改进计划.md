# 知识库文档解析与切分改进计划

> 编写日期：2026-09-30
> 适用范围：`ai-python/app/rag/ingestion/`（解析 → 清洗 → 切分 → 质量检查）
> 配套文档：[企业级RAG知识库与检索评估指南](./企业级RAG知识库与检索评估指南.md)

---

## 1. 背景与原则

### 1.1 资料特点

医院提供的资料以 **PDF 和 Word** 为主，内容大部分是文字，另有一些表格、数学公式和化学式，图片很少。

### 1.2 运行环境

线上服务器配置为 **2 核 4G、无 GPU**，同时运行着 Java 后端、ai-python 和 Chroma。任何需要 torch 或深度学习模型的解析工具（MinerU、Docling、OCR 大模型等）都**不能**部署在这台服务器上。

### 1.3 原则

1. **优先用已有依赖和自研代码**：pypdf、python-docx 能解决的，不引入新库。
2. **问题驱动升级**：只有当质量报告或评估集证明某类问题确实存在、并且影响回答时，才考虑引入更重的工具。
3. **重型工具只在离线环境使用**：如果将来确实需要 MinerU 这类工具，放在开发机上离线解析，服务器只导入解析结果，绝不在线上常驻。
4. **每次改动都有测试和验收标准**：切分规则影响全部文档，改动必须能用样本文档对比前后效果。

## 2. 现状速览

### 2.1 已经做得不错的

| 能力 | 位置 |
| --- | --- |
| 统一的中间结构 `ParsedDocument` / `ParsedElement`：已有标题、段落、表格、公式、图片、页眉、页脚等元素类型，以及 `search_text`、`structured_table`、`asset_refs` 字段 | `rag/ingestion/models.py` |
| Word 解析：按标题样式分章节；表格支持合并单元格，能识别重复表头 | `rag/ingestion/parsers.py` 中的 `NativeDocumentParser._parse_docx` |
| 文档分类后按类型路由到不同切分策略（FAQ、流程、制度等 7 类） | `rag/ingestion/chunking.py` 中的 `ChunkingRouter` |
| 扫描页检测：没有文字层的 PDF 页会被标为阻断级问题，禁止发布 | `rag/ingestion/quality.py` 中的 `pdf_page_without_extracted_text` |

### 2.2 存在的问题

| 编号 | 问题 | 影响 | 原因 |
| --- | --- | --- | --- |
| P1 | Word 页眉页脚被切进正文 | 最后一个章节的片段混入"××医院 内部资料 第 X 页"等噪声 | `_parse_docx` 把页眉页脚追加到元素列表末尾，`cleaner.py` 不过滤，切分时继承了最后一个章节的 `section_path` |
| P2 | PDF 页眉页脚混在正文里 | 每页正文开头或结尾都带着页眉、页码 | pypdf 的 `extract_text()` 不区分文字位置 |
| P3 | 表格被切散 | 表格被拆到两个片段后，后半截没有表头，数值失去含义 | `_split_units_independently` 会把章节文本按换行和 `。！？；;` 拆成句子再重新打包，表格的每一行都被当成一个句子 |
| P4 | 公式和解释文字分离 | 片段里只有一串公式，看不出它在算什么 | 同上，公式元素被当成普通的一行 |
| P5 | Word 公式丢失结构 | \(x^2\) 变成 `x2`，\(\frac{a}{b}\) 变成 `ab`，LLM 可能读错计算方法 | OMML 公式只把文字片段拼接起来（`concatenated_math_text_runs`） |
| P6 | Word 化学式上下标丢失 | `Ca²⁺` 变成 `Ca2+`，`H₂O` 变成 `H2O` | `paragraph.text` 不保留文字的上下标格式 |
| P7 | PDF 没有标题层级 | PDF 基本退化成"没有章节"的一大段，按章节切分失效 | pypdf 只抽纯文本，没有用字号信息 |
| P8 | PDF 表格识别不出来 | 表格变成一行行用空格隔开的文字 | pypdf 没有表格识别能力 |
| P9 | 误启用 Docling 的风险 | 服务器上一旦装了 Docling，上传 PDF 时可能内存耗尽 | `default_parser_for` 的逻辑是"装了就自动用" |

## 3. 分阶段计划

### 阶段一：切分与清洗修复（纯代码改动，无新依赖）

**目标**：解决 P1、P3、P4、P9。这几项对全部现有文档都生效，收益最大。

| 任务 | 改动 | 验收标准 |
| --- | --- | --- |
| 1.1 页眉页脚不参与切分 | 在切分入口（或清洗阶段）过滤 `HEADER`、`FOOTER` 元素，把去重后的文本放进文档元数据（例如 `metadata["page_furniture"]`），便于审核时查看 | 带页眉页脚的 Word 样本，所有片段里都不出现页眉页脚文字 |
| 1.2 表格作为整体不可切断 | `_sentence_units` 不再拆分 `TABLE` 元素。表格不超过 `max_tokens` 时单独成段；超长时按行切，每段开头重复表头行（`structured_table.header_rows`），并带上表格标题 | 1）小表格完整出现在一个片段里；2）超长表格的每个片段都以表头开头；3）表格行不会和正文句子混在同一片段 |
| 1.3 公式和上下文绑定 | 公式元素不单独成段，和前一句（通常是"计算公式如下："）以及后一句（通常是"其中 x 表示……"）打包在一起 | 公式片段都包含至少一句解释文字 |
| 1.4 Docling 改为显式开关 | `default_parser_for` 改为读取配置（例如环境变量 `RAG_PARSER=native`），默认使用原生解析器；只有显式配置时才用 Docling | 服务器上即使安装了 Docling，未配置时也不会启用 |

**测试**：在 `tests/unit/test_ingestion_pipeline.py` 中补充用例：带页眉页脚的 Word、带长表格的 Word、带公式的 Word。

### 阶段二：Word 增强（零依赖或自研）

**目标**：解决 P5、P6。

| 任务 | 做法 | 验收标准 |
| --- | --- | --- |
| 2.1 化学式上下标还原 | 遍历段落的文字片段（run），根据 `font.subscript` / `font.superscript`：展示用的 `text` 转成 Unicode 上下标（`H₂O`、`Ca²⁺`），检索用的 `search_text` 保留普通字符（`H2O`、`Ca2+`），方便关键词检索命中 | 样本中的化学式在 `text` 里带正确的上下标 |
| 2.2 OMML 公式转 LaTeX（自研小转换器） | OMML 本身是结构化的 XML，常见结构只有十几种：上标 `m:sSup`、下标 `m:sSub`、上下标 `m:sSubSup`、分式 `m:f`、根号 `m:rad`、括号 `m:d`、求和或积分 `m:nary`、函数 `m:func`、矩阵 `m:m` 等。写一个递归转换函数，覆盖这些结构即可（约 100～200 行）；遇到不认识的结构时，退回现有的"拼接文字"方式并在元数据中标记 | 1）常见医学公式（BMI、肌酐清除率、体表面积、剂量换算）能转成正确的 LaTeX；2）转换失败时有标记，质量报告能看到 |
| 2.3 公式的检索文本 | `text` 存 LaTeX，供 LLM 阅读和前端渲染；`search_text` 存 LaTeX 去掉命令后的变量名，加上前后解释文字 | 按公式名称（如"肌酐清除率"）能检索到公式片段 |

**备选方案**：如果自研转换器遇到大量无法覆盖的复杂公式，再考虑用 Pandoc 转换。Pandoc 是一个独立程序，通过子进程调用，内存占用很小，可以在服务器上运行。

### 阶段三：PDF 增强（优先用 pypdf 已有能力）

**目标**：解决 P2、P7，按需解决 P8。

pypdf 的 `page.extract_text(visitor_text=回调函数)` 会把每段文字的**坐标和字号**传给回调函数，不需要新依赖就能拿到版面信息。

| 任务 | 做法 | 验收标准 |
| --- | --- | --- |
| 3.1 PDF 页眉页脚剔除 | 两种规则同时使用：1）**位置规则**：页面顶部和底部各约 6% 区域内的文字作为页眉页脚候选；2）**重复规则**：把数字替换成占位符后，同一行文字出现在超过一半页面的相同位置，就判定为页眉页脚。两条规则都命中才剔除，避免误删正文 | 样本 PDF 的片段里不出现页眉和页码 |
| 3.2 按字号识别标题 | 统计全文最常见的字号作为正文字号；明显更大、加粗、单独成行的短文本判定为标题，按字号从大到小分成 1～3 级。另外，"第X章 / 一、/ 1.1"这类编号格式作为辅助判断 | 结构清晰的 PDF 能分出章节，`section_path` 不为空 |
| 3.3 合并跨页段落 | 上一页最后一段没有句号结尾、下一页第一段不是标题时，把两段合并 | 跨页的句子不会被切断 |
| 3.4 PDF 表格（按需） | 先观察：如果质量报告和人工抽查发现 PDF 表格问题确实影响回答，再引入 **pdfplumber**（MIT 许可，纯 Python，轻量）。它对有边框线的表格识别效果较好，识别结果转成现有的 `StructuredTable` | 有边框线的表格能还原出行列结构 |

**PDF 公式的处理策略**：电子版 PDF 里的公式只能抽出近似文本，这是纯文本方案的固有局限。处理顺序：

1. **请医院优先提供 Word 原件**（最有效，零成本）；
2. 片段保留 `page_numbers`，涉及公式的回答附上"详见原文第 X 页"；
3. 个别公式特别多、又没有 Word 原件的 PDF，在开发机上离线处理（见第 5 节）。

### 阶段四：质量门禁补强

**目标**：让问题**自动暴露**，而不是等用户发现回答错了。在 `quality.py` 中增加以下规则（都是确定性规则，不依赖模型）：

| 规则编码 | 级别 | 触发条件 | 提示 |
| --- | --- | --- | --- |
| `pdf_scanned_document` | 阻断 | 文字覆盖率（`text_coverage`）低于 50% | 请上传电子版 PDF 或 Word 原件 |
| `pdf_no_structure` | 警告 | PDF 超过 5 页但没有识别出任何标题 | 章节结构缺失，检索效果可能较差 |
| `header_footer_residue` | 警告 | 多个片段中出现相同的短文本行 | 可能有未剔除的页眉页脚 |
| `formula_conversion_fallback` | 警告 | 有公式未能转成 LaTeX | 公式可能显示异常，建议人工核对 |
| `formula_garbled_suspected` | 警告 | PDF 片段中孤立符号（如 `= + / ×` 或单个字母）占比异常高 | 疑似公式乱码，建议提供 Word 原件 |
| `table_oversized` | 提示 | 表格按行切成超过 N 段 | 大表格已拆分，确认每段表头正确 |

质量状态沿用现有的"通过 / 需审核 / 阻断"三级。前端知识库管理页面展示这些问题，由管理员决定是否发布。

## 4. 问题排查手册

以后遇到问题时，按下表从左往右尝试，**能在左边解决就不往右走**。

| 遇到的问题 | 如何发现 | 第一步：自研或规则 | 第二步：轻量库（服务器可运行） | 第三步：重型工具（仅离线） |
| --- | --- | --- | --- | --- |
| 片段里有页眉、页码 | 质量报告 `header_footer_residue`；人工抽查 | 位置规则 + 跨页重复规则 | pdfplumber 提供更精确的坐标 | MinerU 版面检测会自动剔除 |
| PDF 没有章节结构 | 质量报告 `pdf_no_structure` | 字号统计 + 编号格式（第X章、一、1.1） | pdfplumber 可以读字体名称，便于判断加粗 | MinerU / Docling 版面识别 |
| PDF 表格变成乱文字 | 人工抽查；评估集中涉及表格的问题答错 | 请求提供 Word 原件 | pdfplumber `extract_tables()`（适合有边框线的表格） | MinerU 表格识别（支持无框线表格、跨页表格） |
| Word 公式显示错误 | 质量报告 `formula_conversion_fallback` | 补充自研转换器支持的 OMML 结构 | Pandoc 转换 | — |
| PDF 公式乱码 | 质量报告 `formula_garbled_suspected` | 请求提供 Word 原件；回答附原文页码 | — | MinerU 公式识别（输出 LaTeX） |
| 化学式上下标丢失 | 人工抽查 | Word：读取文字片段的上下标格式；PDF：按字号变小、位置下沉判断 | — | — |
| 扫描件、图片 PDF | 质量报告 `pdf_scanned_document`（阻断） | 拒绝入库，请求提供电子版 | RapidOCR（ONNX 版，约 100～300MB 内存；建议仍在离线环境运行） | MinerU OCR |
| 化学结构式图片需要识别 | 业务提出需求 | 用图注和上下文中的药名建立检索文本，原图作为附件展示 | — | MolScribe 识别成 SMILES，作为元数据保存 |
| 片段语义不完整、检索不到 | 评估集 Recall@k 低 | 在片段前拼接"文档标题 > 章节路径"再向量化；调整片段长度 | — | — |

## 5. 升级触发条件与离线解析方案

### 5.1 什么时候才考虑引入重型工具

满足以下任一条件，再启动离线解析方案：

- 扫描件或没有原件的图片型 PDF 超过资料总量的 10%，且无法换成电子版；
- 公式很多、又没有 Word 原件的 PDF，在评估集中导致明显的答错；
- 无框线表格、跨页表格大量出现，pdfplumber 处理不了；
- 业务明确需要识别化学结构式图片。

### 5.2 离线解析的做法

```
开发机（内存 ≥ 16GB，低频手动执行）              线上服务器（2核4G）
────────────────────────────────              ──────────────────────
MinerU（纯 CPU 模式）解析少量难处理的文档
  → 转换成 ParsedDocument 格式的 JSON
  → 人工抽查                           ──上传──►  清洗 → 切分 → 质量检查 → 向量化
```

需要的改动：服务器新增一个"导入已解析结果"的接口，接收 `ParsedDocument` 格式的 JSON，跳过解析步骤，直接进入清洗和切分。这样重型工具永远不会接触线上服务器。

**许可证提醒**：MinerU 3.1 起采用基于 Apache 2.0 的自定义许可，可以商用；但对外提供在线服务时，需要在产品界面或公开文档中注明使用了 MinerU。PyMuPDF 是 AGPL 许可，不建议引入。

## 6. 资料上传规范（建议同步给医院）

1. **首选 Word 原件（.docx）**：结构、表格、公式保留得最完整；
2. **其次是电子版 PDF**：从 Word 或 WPS 直接导出，能选中文字；
3. **不接受扫描件**：系统会自动拦截；
4. 公式请用公式编辑器输入，不要截图粘贴；
5. 表格请使用真正的表格，不要用空格或制表符对齐模拟表格；
6. 标题请使用"标题 1 / 标题 2"样式，不要只靠加粗和调字号。

---

## 7. 验证方法

1. **样本文档集**：从医院资料中挑 20～30 份典型文档（带页眉页脚、长表格、公式、化学式的各若干份），放在测试资源目录中，作为固定的回归样本。
2. **每个阶段完成后对比**：对样本集分别导出改动前后的片段，人工检查：
   - 片段中是否还有页眉页脚；
   - 表格是否完整、每段是否带表头；
   - 公式是否可读、是否和解释文字在一起；
   - 章节路径是否正确。
3. **检索层验证**：按[企业级RAG知识库与检索评估指南](./企业级RAG知识库与检索评估指南.md)中的方法建立评估集，比较改动前后的 Recall@5 和 MRR，确认切分改进确实带来了检索提升。

## 8. 优先级总结

| 阶段 | 内容 | 新增依赖 | 优先级 |
| --- | --- | --- | --- |
| 一 | 页眉页脚过滤、表格和公式不可切断、Docling 显式开关 | 无 | **最高**，对全部现有文档生效 |
| 二 | Word 化学式上下标、OMML 转 LaTeX | 无（Pandoc 作为备选） | 高 |
| 三 | PDF 页眉页脚、标题识别、跨页段落合并 | 无（pdfplumber 按需引入） | 中 |
| 四 | 质量门禁补强 | 无 | 中，建议和阶段一、三同步进行 |
| 离线方案 | MinerU 等重型工具 | 仅开发机 | 按需，满足触发条件才做 |
